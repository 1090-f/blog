# 部署四问面试话术（blog 项目版）

> 用法：每题先用加粗的「定调句」开头（10 秒内说完），再按 1-2-3 展开，最后主动抛一个 trade-off。
> 最后一节「诚实边界」告诉我们哪些能指着代码讲、哪些只能讲成设计意图，务必先看那一节。

---

## 问题一：你的服务怎么部署的？

**定调句**：我把部署拆成「构建」和「运行」两段——在 CI 里构建镜像，服务器只负责拉镜像重启，不做任何编译。

**展开**：

1. **构建阶段**：`docker/Dockerfile` 是三段式多阶段构建。第一段用 `node:20-alpine` 编前端；第二段用 `golang:1.24-alpine` 编后端，二进制是 `CGO_ENABLED=0` 静态链接、带 `-trimpath -ldflags="-s -w"`；第三段用 `alpine:3.20`，只拷二进制和 `web/dist` 进去。
   所以最终运行镜像里既没有 Go 也没有 Node，体积和攻击面都小很多。
2. **运行阶段**：`docker/compose.yaml` 里两个服务。app 用 `restart: unless-stopped` 守护进程；MySQL 用 `mysqladmin ping` 做健康检查，app 侧写 `depends_on: db: condition: service_healthy`，避免应用比数据库先起来、连不上直接退出。
3. **数据落地**：两个具名卷 `mysql_data` 挂 `/var/lib/mysql`、`app_uploads` 挂 `/app/uploads`，容器重建数据还在。

**举例（现成命令）**：

```bash
docker compose --env-file docker/.env -f docker/compose.yaml up -d --build
curl -f http://localhost:8080/health
curl -f http://localhost:8081/health
```

**主动补一句（重要的加分点）**：这条链路里我现在要补的是镜像 tag 唯一化。目前 compose 用的是 `build:`，等于在目标机上现编。生产我会把顺序倒过来——CI 构建时打 `blog:${GIT_SHA}` 推到 registry，服务器改成 `image:` 直接拉。这样回滚就是换一个 tag，不用重新编译，而且线上跑的是哪次提交是可追溯的。

**追问预案**：

| 追问 | 答法 |
|---|---|
| 为什么不用 `latest` 标签？ | 镜像是不可变交付物，`latest` 会被覆盖，回滚时没有「上一个」可切，也说不清线上跑的是哪次提交 |
| 为什么 `CGO_ENABLED=0`？ | 静态链接，能直接放到没有 glibc 的 alpine 上；否则要换 debian 基础镜像，体积从几十 MB 涨到几百 MB |
| 为什么容器里不用 root？ | Dockerfile 里 `addgroup/adduser app` 后 `USER app`，容器被突破时降低影响面 |
| 前端为什么要单独一段构建？ | 运行时不需要 Node 工具链，编译产物是静态文件，构建依赖不该进运行镜像 |

## 问题二：怎么做到发布不中断、出问题怎么办？

**定调句**：我用健康检查定义「这次发布算不算成功」，失败就退回上一个镜像 tag；目前是单实例，所以我的目标是**快速回滚**，不是零中断——多副本滚动替换是我下一步的演进方向。

**展开**：

1. **健康检查**：应用暴露 `GET /health`（`internal/router/groups.go` 注册，公开端口和管理端口各一个）。容器状态要走到 `healthy` 才算真正起来，而不是「进程还在」就算。
2. **发布判定**：新版本起来后打 `/health` 返回 200 → 发布成功；超时或非 200 → 判定失败，不再放流量。
3. **回滚**：因为镜像不可变、tag 是 commit sha，回滚就是把 tag 换回上一个再 `up -d` 重建，成本是一次拉镜像，通常秒级到十几秒。

**主动交代代价（这段最能区分「跑过 docker」和「做过部署」）**：

> 单实例下 `up -d` 重建容器会有一个短暂空窗，这是我现在方案的代价。要消掉它需要两个前提：一是多副本，Nginx 后面挂两个实例、逐个替换（先起新的、健康检查过了再停旧的，这就是滚动发布）；二是会话状态不能存在进程内存里。我这套用 JWT，认证状态不依赖服务端 session，所以扩副本是很自然的一步——如果当初用 Redis 存 session，扩副本时就得额外处理粘性和共享状态。

**追问预案**：

| 追问 | 答法 |
|---|---|
| `/health` 返回 200 说明什么？ | 要能说清它探到什么。只返回 200 说明进程活着；要真正可用，它应该内部探一次 MySQL 连通性再返回 |
| 迁移和代码不兼容时怎么回滚？ | 迁移要向前兼容：先加字段不改字段（expand），代码切换完成后再清理旧字段（contract）。回滚只回代码不回数据 |
| 你怎么发现发布失败了？ | 健康检查是自动判定，另外要有日志和告警，否则只能等用户反馈 |
| 多个副本同时跑迁移会不会冲突？ | 迁移要幂等、要能加锁，或者干脆拆成独立的迁移步骤在发布前跑一次 |

## 问题三：配置和密钥怎么管？

**定调句**：同一份镜像跑 dev 和 prod，差异全部通过环境变量注入，镜像里不含任何环境相关的配置。

**展开**：

1. **代码层**：`config/config.go` 用 Viper，每个配置项都有默认值，同时支持环境变量覆盖（`BLOG_DATABASE_HOST`、`BLOG_JWT_SECRET` 等）。所以本地不设任何变量也能跑起来，生产注入就生效，代码零改动。
2. **编排层**：compose 里环境变量写成 `${VAR}` 从 `.env` 取，并带默认值，例如 `BLOG_UPLOAD_MAX_SIZE_BYTES: ${BLOG_UPLOAD_MAX_SIZE_BYTES:-5242880}`。`docker/.env.example` 入库作为模板，`docker/.env` 不入库、权限收到 600。
3. **密钥管理**：JWT secret 和数据库密码只存在于 `.env` 或平台的 secret 管理里，不进代码、不进镜像层历史。另外生产不能开 `BLOG_ADMIN_BOOTSTRAP_ENABLED`——它是有意留的首次初始化开关，但忘记关掉就等于留了一个默认口令入口。

**主动说一个自己发现的坑（加分）**：

> 我发现 `docker/.env.example` 里 bootstrap 默认是 `true`、密码是 `123456`。模板是最容易被直接复制上线的东西，我会把它默认改成 `false`，让「开启初始化」变成一个需要人主动做的动作。

**追问预案**：

| 追问 | 答法 |
|---|---|
| 为什么不给每个环境打一个镜像？ | 那就变成同一份代码产出多个不可复现的产物，测试过的镜像和上线的镜像不是同一个；而且密钥会被打进去 |
| 密钥怎么轮换？ | JWT secret 轮换会让所有已签发 token 立即失效，要么接受一次全员重新登录，要么支持双密钥过渡验签 |
| 配置错了怎么办？ | 启动时做校验（比如两个端口不能相同），错了直接启动失败，不要带着错配置跑起来 |

## 问题四：数据怎么保证不丢？

**定调句**：分两类数据——MySQL 业务数据靠持久化卷加定时逻辑备份，uploads 用户文件靠独立卷加同步备份；核心原则是**没验证过能恢复的备份不算备份**。

**展开**：

1. **持久化**：`mysql_data` 和 `app_uploads` 两个具名卷。文档里专门写了一句：`down` 不要加 `-v`，因为 `-v` 会连卷一起删。
2. **备份**：`mysqldump` 定期导出、上传目录打包或 rsync，而且**备份必须落到另一台机器或对象存储**——同机同盘的备份挡不住整机故障，这是最常见的假安全感。
3. **恢复演练**：定期在干净环境里真的恢复一次，确认备份文件可用、恢复流程走得通。

**追问预案**：

| 追问 | 答法 |
|---|---|
| 备份频率怎么定？ | 由 RPO 倒推：能接受丢多久的数据，就定多密的备份。RTO 决定恢复方式（直接恢复 vs 需要主从切换） |
| 数据量大了 `mysqldump` 撑不住怎么办？ | 换物理备份（XtraBackup）或 binlog 增量 + 主从，dump 会锁表且恢复慢 |
| 为什么用具名卷而不是绑定挂载？ | 具名卷由 Docker 管理，不用操心宿主目录权限和 uid 映射，换机器部署也不用管路径。代价是数据不直观可见，要靠 `docker volume ls` 找 |
| 上传目录和数据库不一致了怎么办？ | 先备份后操作，能接受短暂的引用失效；真要强一致就得上对象存储 + 数据库事务外的补偿流程 |

## 诚实边界：哪些能讲、哪些要改口

### 现在就能指着代码讲的（有实据）

- 三段式多阶段构建、静态二进制、`-trimpath -ldflags="-s -w"`
- 非 root 用户运行（`USER app`）
- `restart: unless-stopped` 守护
- MySQL 健康检查 + `depends_on: service_healthy` 启动顺序
- 具名卷 `mysql_data` / `app_uploads`、`down` 不加 `-v`
- 环境变量外部化（Viper 默认值 + 环境变量覆盖）、`.env.example` 入库而 `.env` 不入库
- 8080 公开 / 8081 管理双端口分离
- `GET /health` 健康检查端点（两个端口各一个）
- CI 跑 `go test ./...`、`npm ci`、`npm run lint`、`npm run build`

### 目前只是设计意图，必须改口说成「我会这么做」

| 内容 | 不要说成 | 应该怎么说 |
|---|---|---|
| CI 构建并推送镜像 | 「我的 CI 会推镜像」 | 「现在 CI 只做测试和构建校验，镜像推送是我正在补的一环，做法是……」 |
| 镜像 tag 用 commit sha | 「我们线上用 sha tag」 | 「生产我会用 sha tag，现在是 compose 本地 `build:`，这一点正在改」 |
| 自动回滚 | 「失败会自动回滚」 | 「回滚动作现在是手动的，把 tag 换回去重建；自动化是下一步」 |
| 多副本滚动发布 | 「我们滚动发布」 | 「单实例的代价是重建时有空窗，多副本滚动是我的演进方案，前提是 JWT 无状态」 |
| 定时备份 / 恢复演练 | 「有备份策略」 | 「备份还停留在文档里的建议，我会先落一个 mysqldump + 异地存放的 cron」 |
| 反向代理 / HTTPS | 「后面挂了 Nginx」 | 「反向代理还没进仓库，计划是 Caddy 或 Nginx 前置，TLS 在它那里终止」 |
| 日志采集与告警 | 「有监控」 | 「目前只有 compose logs，日志轮转和告警是我下一步要补的」 |

### 三条通用技巧

1. **先给定调句，最后主动抛 trade-off**，不要等面试官追问。主动说出代价，比被问出来时辩解得分高得多。
2. **别把单机 Compose 讲成 K8s**。正确姿势是：「我现在这么做是因为规模还小、部署最简；规模上来的演进路径是多副本 + 滚动发布，再往上才是 K8s。」面试官考的是你知道自己方案的边界。
3. **每题都落到具体文件和命令**，别停在名词上。「我用 multi-stage build」是名词，「node 编完前端、Go 编出静态二进制、最后只拷产物进 alpine」才是细节。
